## 2026-04-28 (Add Recipe wizard: bogus macros + image upload root cause + missing resolveSupabaseId)
- **Image upload was fundamentally broken on iOS — Blob path corrupts request body** — root cause was NOT just silent error handling. `lib/imageUpload.ts` used `await fetch(file://...).blob()` and passed the resulting `Blob` to `supabase.storage.upload()`. On RN/iOS this combination silently ships zero (or partial) bytes — `blob.size` reports correctly so client-side validation passes, but the Supabase JS SDK's request serializer reads empty data. The file at the public URL ends up empty/unreadable. Supabase docs explicitly require an `ArrayBuffer` or `Uint8Array` on RN, not `Blob`. Fixed by rewriting `validateImageForUpload` to use `expo-file-system` v19's `File.bytes()` which returns a real JS `Uint8Array` that bypasses the broken fetch-blob bridge. Return shape changed from `{ blob, contentType }` to `{ data: Uint8Array, contentType, byteLength }`; both call sites updated (`AddRecipeWizard.uploadImage`, `app/edit-profile.tsx:handlePickAvatar`). MIME inference now uses URI extension instead of `blob.type` (with optional `mimeOverride` for ImagePicker assets that lack extensions). `__tests__/lib/imageUpload.test.ts` rewritten to mock `expo-file-system.File`. `expo-file-system@19.0.22` is already pulled in transitively via `expo@54.0.34` — no new dependency.
- **AddRecipeWizard silently dropped failed image uploads** — when the upload still failed for any other reason (RLS denial, missing bucket, network), `uploadImage` swallowed every non-`ImageValidationError` and returned `null`; `handleSubmit` then created the recipe row with `image_url: null` and showed no feedback. Fixed in `components/AddRecipeWizard.tsx`: non-validation errors now fire a `Could not upload photo` alert with the underlying error message, and `handleSubmit` aborts (sets `submitError`, returns) when the user attached a photo but `uploadImage` returned null — recipe is NOT inserted, wizard state is preserved so the user can retry. Empty-state path (no photo selected) still saves normally. Operational follow-up: verify `recipe-images` bucket + RLS policies from `supabase/add-recipe-submission.sql` are applied in production via Supabase Studio.
- **`resolveSupabaseId` referenced but undefined — interaction logging silently broken** — `app/(tabs)/discover.tsx` called `resolveSupabaseId(recipe)` in 4 places (lines 745, 771, 1200, 1211) covering grocery_add, view, and cooked interactions. The symbol was never imported nor defined → `ReferenceError` at runtime, swallowed by the `.catch(() => {})` chained on every call. Result: `recipe_interactions` rows for `'view'` / `'grocery_add'` / `'cooked'` were silently NOT being inserted, degrading the scorer's signal and explaining why CLAUDE.md §9 noted only ~3% of cook interactions had a prior view. Fixed: added `resolveSupabaseId(recipe: Recipe): Promise<string>` to `lib/api.ts:1497` — returns `recipe.supabase_id` synchronously when present (the common case from `fetchScoredDeck` / `fetchDiscoverRecipes`), falls back to a `recipes.select('id').eq('external_id', ...)` lookup, throws when neither identifier is available. Imported into `discover.tsx`.
- **Macros hallucinated for sparse recipes** — user submitted a community recipe with a single ingredient ("garlic") and got 18 g protein per serving. Root cause: `api/macros.ts:estimateWithClaude` sent Claude a one-line prompt with no per-ingredient breakdown step and no validation, hardcoded "Assume 4 servings", and no sanity bounds on the response. With sparse input Claude fabricated plausible-looking macros for whatever recipe it imagined the title implied. Fixed in three layers: (1) new `isTooSparseForMacros` gate refuses to call Claude when there are <3 ingredients OR fewer than half have quantities — handler returns `{ macros: null, reason: 'insufficient_ingredients' }`; (2) prompt rewritten to force a per-ingredient → sum → divide-by-servings reasoning chain and to return a `confidence: low|medium|high` flag, with the user's actual `servings` count threaded through (`MacrosRequestSchema` gained an optional `servings` field; `enrichCommunityRecipe` and `AddRecipeWizard` now forward it); (3) `isImplausibleMacros` post-validator rejects outputs where protein·4 > calories·1.1, where Atwater-summed kcal mismatches reported calories by >50%, or where confidence=low + no protein source + protein > 5 g. Rejected outputs now save nothing (DB `macros` stays null, UI hides pills). Tests in `__tests__/api/macros.test.ts` (9 cases) cover all three layers.

## 2026-04-28 (Second security audit batch)
- **GitHub PAT embedded in `.git/config`** — remote URL was `https://ghp_…@github.com/jacobmkim/projectX.git`. Anyone with filesystem access (machine theft, OS image, screen-share, support session) reads the token and gets full write to the private repo. Fixed: `git remote set-url origin https://github.com/jacobmkim/projectX.git`. User must revoke the PAT at https://github.com/settings/tokens and reauthenticate via Git Credential Manager.
- **`.gitignore` allowed env-variant + native-build leaks** — only `.env` and `.env.local` were ignored, so `.env.production`/`.env.staging` would be committable. `ios/` and `android/` were also untracked-but-not-ignored, so `expo prebuild` outputs (signing keys, `GoogleService-Info.plist`, `google-services.json`) could land in commits. Fixed: `.env.*` block with `!.env.example`; added `ios/`, `android/`, `GoogleService-Info.plist`, `google-services.json`, `*.xcuserstate`.
- **Auto-approved community recipes** — `insertCommunityRecipe()` in `lib/api.ts:1994` hardcoded `moderation_status: 'approved'`, so every submission appeared in Discover immediately. Fixed: default to `'pending'`. Discover query already filters `moderation_status = 'approved'`, so submissions are now hidden until manually flipped via Supabase Studio. Submitter still sees their own under Recipes → Mine (filtered by `submitted_by`); a "Pending review" badge already exists in `app/(tabs)/recipes.tsx:112`. Test in `__tests__/lib/insertCommunityRecipe.test.ts` updated.
- **Production RLS regression — `recipes` UPDATE/INSERT** — production policies still had `((auth.uid() = submitted_by) OR (submitted_by IS NULL))`. The `supabase/fix-recipes-rls.sql` one-shot migration was never applied. Result: any signed-in user could `UPDATE` any of the 1,506 curated recipes (steps, title, anything) and could `INSERT` rows with `submitted_by = NULL` to masquerade as curated content. Fixed: applied `supabase/add-security-hardening-202604.sql` migration tightening both policies to `auth.uid() = submitted_by`. Also folded into `schema.sql:213-216` so a fresh rebuild won't regress.
- **`recipe_flags` flag-spam** — no per-(user, recipe) uniqueness, so a single user could insert thousands of flag rows for the same recipe. Fixed: `CREATE UNIQUE INDEX uq_recipe_flags_user_recipe ON recipe_flags(flagged_by, recipe_id)` (partial index, NOT-NULL only) in the same migration.
- **Instacart partner-ID UTM not URL-encoded** — `api/instacart-cart.ts:101` inlined `${partnerId}` raw. Misconfigured env (`7220009 & evil=1`) would corrupt the redirect URL. Fixed: `encodeURIComponent(partnerId)`.
- **`/api/admin-recipes` no rate limit** — secret check is `timingSafeEqual` so brute force is impractical, but no defense-in-depth wall. Fixed: `rateLimitIP(getClientIP(req), 'admin-recipes', 30, 3600)` before the secret check; on `!success` returns 429 with `Retry-After`.
- **Stray prod log in `app/reset-password.tsx:74`** — `console.log('No tokens found in URL')` fired in release builds. Wrapped in `if (__DEV__)`.
- **Cook-funnel trigger DEFERRED** — the audit recommended a DB trigger rejecting `recipe_interactions` `'cooked'` inserts without a prior `'view'` row, to close the brigade vector where users self-INSERT a fake cook then submit a review. Investigation showed only ~3% of existing `cooked` rows have a prior `'view'` (legacy data + view-logging gap), so the trigger would block legitimate cooks. Documented as open in CLAUDE.md §9; revisit in Phase 5 with a moderation queue or stronger account-creation gate.

## 2026-04-27 (Audit batch — high-severity security)
- **`waitlist` table had no RLS** — `ALTER TABLE waitlist ENABLE ROW LEVEL SECURITY` (no policies → service-role only). Any signed-in client with the anon key could otherwise `select * from waitlist` and exfiltrate every signup email. Migration: `supabase/add-waitlist-rls.sql`.
- **`recipe_reviews` had no migration / RLS in repo** — created `supabase/add-recipe-reviews.sql` with public SELECT, INSERT scoped to `auth.uid() = user_id` AND a `cooked` interaction must exist for the recipe, UPDATE/DELETE owner-only, UNIQUE(recipe_id, user_id) to prevent multi-review spam.
- **`recipe_flags` had no migration / RLS in repo** — created `supabase/add-recipe-flags.sql` with INSERT scoped to `flagged_by = auth.uid()`, SELECT/DELETE owner-only. Closes the risk where `clearFlaggedRecipes()`'s `delete().not('id', 'is', null)` could wipe the global flag table.
- **`profiles` join exposure** — discover/reviews queries embedded `submitter:profiles!recipes_submitted_by_fkey(...)` which either silently returned null (broken feature) or relied on a permissive policy that exposed `taste_profile`, `weekly_budget`, `push_token`, `dietary_goals`, `last_cooked_date`. Fixed: `supabase/add-profiles-public-view.sql` creates a SECURITY DEFINER `profiles_public` view projecting only `id, name, username, avatar_url, recipes_submitted_count, meals_cooked_count`. Updated all 5 join sites in `lib/api.ts` to embed `profiles_public` instead of `profiles`. Migration also drops any non-baseline SELECT policy on `profiles`.
- **IDOR on `/api/macros`** — service-role `update().eq('id', supabaseId)` let any authenticated user overwrite any recipe's macros. Fixed in `api/macros.ts:saveMacrosToDB`: now reads the recipe first and only writes when (a) it's a curated recipe with no macros (legitimate backfill) or (b) the caller is the recipe's `submitted_by`.
- **`SEED_SECRET` accepted as cron auth fallback** — both `api/cron/streak-reminders.ts` and `api/cron/taste-notifications.ts` accepted either `CRON_SECRET` or `SEED_SECRET`. A leaked dev secret could trigger push-notification floods. Fixed: cron now requires `CRON_SECRET` only, with `timingSafeEqual` to avoid string-comparison timing leaks.
- **Sentry PII + Session Replay leak** — `app/_layout.tsx` had `sendDefaultPii: true`, `enableLogs: true`, and `mobileReplayIntegration()` recording 10% of sessions / 100% of errors. Replay captured rendered screens including bearer tokens in dev panes, taste profiles, names. Fixed: `sendDefaultPii: false`, replay disabled, `beforeSend` redacts `Authorization` and `Cookie` headers.
- **Deep-link substring match (reset-password phishing)** — `app/_layout.tsx` matched `mori://reset-password` anywhere in the URL via `String.includes`, so `https://evil.com?x=mori://reset-password#access_token=…` would route the user to the reset flow with attacker-controlled fragments. Fixed: `Linking.parse` + strict `scheme === 'mori' && hostname === 'reset-password'` check.
- **`savedStore` lost saves on cold start** — `partialize` only persisted `mealPrepIds`. Optimistic offline saves were lost on relaunch; if `loadSavedRecipes()` was slow, `isSaved()` returned false → duplicate optimistic insert + duplicate Supabase upsert. Fixed: persist `savedRecipes` and `_removedPositions` alongside `mealPrepIds`.
- **Image upload size/MIME validation** — `AddRecipeWizard.uploadImage` and `edit-profile.handlePickAvatar` both did `fetch(uri).blob()` then forced `contentType: 'image/jpeg'` regardless of actual type, with no size cap. A 20 MB HEIC ≈ 60 MB peak in JS memory → iOS app kill, plus egress-abuse vector. Fixed: new `lib/imageUpload.ts` `validateImageForUpload()` rejects empty/oversize blobs (5 MB recipes, 2 MB avatars), allowlists JPEG/PNG/WebP/HEIC, and returns the actual `contentType` for the upload.
