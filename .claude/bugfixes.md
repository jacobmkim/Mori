## 2026-05-05 (Stray wide-open RLS policy on `recipe_flags` — re-tightened)
- **Supabase security advisor flagged `recipe_flags` with `rls_policy_always_true`** — production had a fourth policy `Authenticated users can manage flags` for `ALL` actions on the `authenticated` role with `USING (true) WITH CHECK (true)` sitting alongside the scoped insert/select/delete trio applied 2026-04-27 (`supabase/add-recipe-flags.sql`). Postgres OR-merges permissive policies, so the wide-open one nullified the trio: any signed-in user could `UPDATE`/`DELETE` flag rows owned by other users, and `DELETE FROM recipe_flags` (no WHERE) would have wiped every user's "don't show me again" list globally — exactly the vector bugfixes.md:86 (04-27) claimed to close. Origin unknown — not present in any migration in `supabase/`; likely hand-applied via Supabase Studio before the 04-27 hardening, then never dropped when the scoped trio was added (`add-recipe-flags.sql` does `DROP POLICY IF EXISTS` for the three new policy names but doesn't touch others). Fix: new migration `supabase/add-security-cleanup-202605.sql` drops the offending policy. Applied via MCP. Verified post-apply: `pg_policies` now lists only the scoped trio; advisor no longer reports `rls_policy_always_true` on the table.
- **Pre-drop code-path audit** — every site that touches `recipe_flags` traced and confirmed covered by the remaining scoped policies: `flagRecipe` (INSERT, [lib/api.ts:1934](lib/api.ts#L1934)), `getFlaggedRecipes` (SELECT, [lib/api.ts:1952](lib/api.ts#L1952), now correctly returns only the caller's rows — which matches the function's UI semantic), `clearFlaggedRecipes` (DELETE, [lib/api.ts:1970](lib/api.ts#L1970), now scoped to caller's rows — exactly the documented 04-27 behavior), `api/delete-account.ts` and `scripts/dedupe-recipes.mjs` use service-role and bypass RLS. ## 2026-04-29 (Streak counter showed stale value forever — flame-out state on broken streak)
- **A user reported their streak stuck at 10 days even though they hadn't cooked in over a week.** Behaviour was by design but misleading: `current_streak` in `profiles` is only mutated inside `updateStreakAndCount()` (called after a "cooked" interaction), so a streak of 10 from 2 weeks ago kept rendering as "10-day streak" until the next cook reset it to 1. The user's mental model ("streak = engagement metric") didn't match the data model ("streak = consecutive cook days"), and the display reinforced the wrong model by never decaying. Fix is presentation-only — DB stays authoritative, display layer reflects whether the streak is still salvageable.
  1. **`getEffectiveStreak(currentStreak, lastCookedDate)` helper in `lib/api.ts`** — returns `currentStreak` when last cook was today or yesterday (still salvageable), else `0`. Pure function, 7 unit tests in `__tests__/lib/effectiveStreak.test.ts`.

When 0, the subtitle pill is hidden, the stat tile shows `0` (not the previous em-dash placeholder), the icon flips from `flame` → `flame-outline`, and both icon + value drop to `colors.textMuted` for a clear "flame-out" treatment. Best-streak tile is unaffected (longest_streak is permanent).
  3. **`api/cron/streak-reminders.ts` had the same root bug** — query was `current_streak > 0 AND last_cooked_date < today`, which fired "🔥 10-day streak at risk" pushes to anyone with a stale streak from weeks ago. ## 2026-04-29 (Instacart sent wrong product — `cleanForSearch` stripped product-defining words)
- **"Canned crushed tomatoes" was being sent to Instacart as just "tomatoes"** — `cleanForSearch()` in [grocery-list.tsx:349-362](app/(tabs)/grocery-list.tsx#L349-L362) ran the ingredient name through three regex strips before passing it as the `name` field to `/api/instacart-cart`. The prep-words regex included `crushed` and the descriptor regex included `canned|frozen|dried|ground|whole|fresh|raw|cooked|boneless|skinless`. All of these change the *product*, not the prep — Instacart matched the bare term "tomatoes" and returned 3 Roma tomatoes for a Tikka Masala order. The `displayText` we send is unchanged ("canned crushed tomatoes"), so the bug was invisible from the UI. Same shape would mis-match: `dried oregano → oregano (fresh)`, `ground beef → beef (steak)`, `boneless skinless chicken breast → chicken breast (could match bone-in)`, `frozen peas → peas (fresh)`.
- **Fix**: removed `crushed` from the prep regex and removed `fresh|dried|ground|whole|boneless|skinless|raw|cooked|canned|frozen` from the descriptor regex. Kept the safe-to-strip words: pure prep verbs (`diced|minced|chopped|sliced|grated|julienned|peeled|deveined|trimmed|cubed|shredded|melted|softened|beaten|divided`), size descriptors (`large|medium|small`), prep adverbs (`finely|roughly|thinly`), and preference flags (`extra-virgin|organic`). Added a comment documenting the rule: don't strip words that name a different SKU.
- **Bug was on our end, not Instacart's** — Instacart received the term we sent and matched it correctly. Our search-name builder was the problem.

## 2026-04-29 (Mine-tab delete silently failed → soft-delete column + browse-path filters)
- **Deleting a community recipe from the Mine tab was a silent no-op** — `handleDeleteSelected` in `app/(tabs)/recipes.tsx` called `supabase.from('recipes').delete().eq('id', id)` but `recipes` had RLS enabled with no DELETE policy ([schema.sql:191](supabase/schema.sql#L191)) — only SELECT/INSERT/UPDATE existed. PostgREST returned success with 0 rows affected; the loop ignored the response and re-rendered the row from `loadMineData()`. Even adding a DELETE policy would have failed at the FK boundary: `swipe_events.recipe_id`, `saved_recipes.recipe_id`, `recipe_interactions.recipe_id`, and `recipe_cohort_affinities.recipe_id` all reference `recipes(id)` without `ON DELETE CASCADE`, so any recipe the owner had ever swiped/saved/viewed (i.e. all of them) would block the delete with a constraint violation. Fix is soft-delete:
  1. **Migration `add_recipes_soft_delete`** — `ALTER TABLE recipes ADD COLUMN deleted_at timestamptz` (nullable, no default → 1,506 existing rows untouched) plus partial index `idx_recipes_active ON recipes(created_at DESC) WHERE deleted_at IS NULL` so the live-recipe hot path stays cheap. Migration file `supabase/add-recipes-soft-delete-202604.sql`; folded into `schema.sql`. No DELETE RLS policy added — soft delete reuses the existing UPDATE policy `auth.uid() = submitted_by`, which guarantees curated rows (`submitted_by IS NULL`) can never be soft-deleted by clients.
  2. **Client switch to UPDATE + error surfacing** — `handleDeleteSelected` now does `supabase.from('recipes').update({ deleted_at: new Date().toISOString() }).in('id', ids).eq('submitted_by', userId)`; on error it pops `Alert.alert('Could not delete', error.message)` instead of silently re-rendering. The `.eq('submitted_by', userId)` is defence-in-depth on top of RLS.
  3. **`deleted_at IS NULL` filter on every browse path** — `fetchDiscoverRecipes` + `fetchAdventureRecipe` in `lib/api.ts`; `loadMineData` in `recipes.tsx`; all 5 explore.tsx queries (Just Added, Quick, High Protein, Trending-by-IDs, search). **Intentionally not filtered**: id-resolved paths (`getRecipesBySupabaseIds`, `getSavedRecipesWithDetails`, the `recipe_interactions → recipes` join in Cooked tab) so users who already saved or cooked a deleted community recipe keep their copy. Meal plan slots (`meal_plans.slots` jsonb), grocery lists (`grocery_lists.recipe_ids`), and collections (`collections.recipe_ids`) hold raw UUIDs with no FK — they continue to resolve via `getRecipesBySupabaseIds` and remain functional.
- **Pre-existing community-visibility leak in Explore — flagged, not fixed in this batch.** Unlike `fetchDiscoverRecipes`, the explore.tsx queries don't gate on `is_public + moderation_status='approved'`. Since the 2026-04-28 default flipped new community submissions to `pending`, those rows have been surfacing in Just Added / Search / Trending. Worth a follow-up commit.

## 2026-04-29 (Scorer overhaul: `favourites_rotation` no longer floods deck with saved recipes)
- **Saved-recipe bonuses stacked, monopolising the deck** — for `eating_style = 'favourites_rotation'` the scorer added +6 for being saved AND a +5 right-swipe history bonus (every saved recipe was right-swiped — same event, double-counted), plus +3-6 grocery_add and dietary/cuisine matches that disproportionately apply to already-saved recipes. Net effect: a just-saved recipe scored ~+11 over an equivalent fresh recipe and re-surfaced on the next deck reload. User reported "it just keeps showing already saved" on the TestFlight build. Fixed five ways in `lib/api.ts`:
  1. **Skip right-swipe boost when currently saved** (`scoreRecipe`, line ~793) — mirrors the existing `unsave` guard. The save IS the right-swipe; counting both was the dominant bug.
  2. **Saved bonus +6 → +3** (line ~735) — favourites still compete but no longer dominate.
  3. **Save-recency cooldown** — new `getSavedAtMap(userId)` queries `saved_recipes.saved_at` once per deck load and is threaded through `fetchScoredDeck` → `scoreRecipe`. Penalty mirrors the cooked-recency one: `−15` if saved <3 days ago, `−6` if <14 days. Just-saved recipes are effectively excluded for two weeks, then taper back in via the +3 bonus.
  4. **`maxPerCuisine` 5 → 2 for `favourites_rotation`** (line ~1003) — cuisine diversity cap is now stricter than `variety`'s 3, so users can't see 5 saved Italian recipes in a row.
  5. **30% saved-share cap with interleave** — new `capSavedShare()` helper splits the post-relaxation deck into saved vs. unsaved, takes at most 30% saved, and interleaves so saved appears at every 4th slot (positions 3, 7, 11, …). Excess saved are appended to the tail so they're still reachable on a long session. Skipped on tiny decks (`< 8` recipes) so the last-resort relaxation can still fill an empty deck.
- **Net behaviour change for `favourites_rotation` users**: a just-saved recipe is suppressed for 14 days, then re-enters as a +3 candidate; the deck is structurally capped at ≤30% saved with unsaved recipes filling the top three slots before any saved appears. Non-rotation users are unaffected — saved recipes are still hard-filtered for them.
- **Tests**: existing 20-test `__tests__/lib/scoreRecipe.test.ts` still passes (`savedAtMap` was added as the 10th positional param after `ratingMap`, so existing `callScore` helpers compile unchanged). 56 tests across the 5 scorer-touching suites green.
